# Development Step 2: Survival Column Candidate Detection + Required Mapping

## Goal

Implement the second development step of the dashboard: help the user identify and confirm the required columns for survival analysis.

The app should not force the user to manually search through tens or hundreds of columns. Instead, it should use the existing column profile from Step 1 to generate ranked candidate lists for:

```text
1. Follow-up / survival time column
2. Event/status column
3. Patient ID column
4. Optional grouping column
```

The user should still confirm the final mapping. The app should **suggest**, not silently decide.

---

## Outcome of Step 2

At the end of this step, the app should be able to produce a validated internal survival configuration object like:

```python
survival_config = {
    "time_col": "time",
    "event_col": "status",
    "event_values": [1],
    "censor_values": [0],
    "id_col": None,
    "group_col": "sex",
    "time_unit": "days"
}
```

This object will be used in later steps for Kaplan–Meier curves and survival summaries.

---

## Scope of Step 2

Implement only:

```text
1. Extended column profiling fields
2. Candidate scoring functions
3. Ranked candidate lists
4. UI for required survival mapping
5. Event/censor value mapping
6. Basic validation of the mapping
7. Session-state storage of survival_config
8. Unit tests for scoring and validation
```

---

## Non-Goals for Step 2

Do **not** implement:

```text
Kaplan–Meier curves
Cox models
Log-rank tests
Number-at-risk tables
Charts tab
Cohort overview tab
Advanced data cleaning
Report export
Database persistence
Multi-user accounts
Time-varying covariates
Start-stop survival format
```

The goal is only to correctly identify and validate the columns needed for future survival analysis.

```text

```

Extend this profile to include additional machine-readable fields needed for scoring.

## New Profile Fields

Add these fields to `profile_dataframe` output:

```text
unique_ratio
numeric_parse_rate
date_parse_rate
min_value
max_value
is_non_negative
is_binary_like
is_low_cardinality
is_id_like
```

## Field Definitions

### `unique_ratio`

```python
unique_ratio = unique_count / non_missing_count
```

If `non_missing_count == 0`, set to `0`.

---

### `numeric_parse_rate`

Percentage of non-missing values that can be parsed as numeric.

Example:

```text
[1, 2, 3, None] -> 1.0
["10", "20", "unknown"] -> 0.67
["Dead", "Alive"] -> 0.0
```

Use:

```python
pd.to_numeric(series, errors="coerce")
```

---

### `date_parse_rate`

Percentage of non-missing values that can be parsed as dates.

Use:

```python
pd.to_datetime(series, errors="coerce")
```

For Step 2, this is only informational. Do not implement date-derived survival time yet.

---

### `min_value` and `max_value`

Only meaningful for numeric-like columns.

If the column is not mostly numeric, set both to `None`.

---

### `is_non_negative`

Boolean.

```text
True if numeric-like and all parsed non-missing values are >= 0
False otherwise
```

---

### `is_binary_like`

Boolean.

True if non-missing unique values are equivalent to one of these binary sets:

```text
{0, 1}
{"0", "1"}
{True, False}
{"true", "false"}
{"yes", "no"}
{"y", "n"}
{"dead", "alive"}
{"event", "censored"}
```

Case-insensitive and whitespace-insensitive for text.

---

### `is_low_cardinality`

Boolean.

True if:

```text
2 <= unique_count <= 20
```

This helps detect grouping/categorical variables.

---

### `is_id_like`

Boolean.

True if:

```text
unique_ratio >= 0.95
AND non_missing_count > 10
```

or if the column name strongly suggests an ID and values are mostly unique.

ID name hints:

```text
id
patient_id
subject_id
record_id
case_id
participant_id
person_id
sample_id
mrn
```

## Time Candidate Logic

A good survival time column usually:

```text
is numeric
is non-negative
has many unique values
is not binary
is not ID-like

```

```python
    "time_to_event",
    "days_to_death",
    "months_to_death"
]
```

## Scoring Rules

Suggested scoring:

```text
+40 if column name contains a time keyword
+25 if numeric_parse_rate >= 0.95
+10 if is_non_negative is True
+10 if unique_count > 10
+5  if missing_percent < 20

-40 if is_binary_like is True
-40 if is_id_like is True
-20 if detected_type is text/categorical and numeric_parse_rate < 0.8
-20 if min_value < 0
```

Clamp final score to:

```text
0–100
```

```python
    ...
```

Return:

```python

```

Errors block future survival analysis.

Warnings do not block.

---

## 10.3 Validation Rules

### Errors

Return errors if:

```text
time_col is missing from df
event_col is missing from df
time_col cannot be parsed as numeric
time_col has no non-missing values
time_col contains negative values
event_values is empty
event_values and censor_values overlap
event_col has no non-missing values
no usable rows remain after applying time/event requirements
```

### Warnings

Return warnings if:

```text
time_col has missing values
event_col has missing values
event_col contains values not mapped to event or censored
time_col contains zero values
id_col is missing or not selected
id_col has duplicates
group_col has fewer than 2 groups
group_col has groups with fewer than 5 rows
event count is very low
censored count is very low
```

For Step 2, do not block low event counts. Just warn.
